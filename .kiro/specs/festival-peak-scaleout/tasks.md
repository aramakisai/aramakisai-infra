# Implementation Plan

本計画は IaC リポジトリの性質上、コード変更に加えて適用と検証の作業を含む。タスク 1 から 4 は本番構成を変更せず、タスク 5 以降が本番に触れる。タスク 0 はノード構成に依存せず、他のタスクの進行と無関係に先行して適用できる。

---

- [x] 0. 画像配信エンドポイントのエッジキャッシュ
  - ノード数に依存せず、本番構成への影響も小さい。ノード増設 (タスク 3 以降) を待たずに先行して適用できる
  - _Requirements: 9.9_

- [x] 0.1 Cache Rule を `/api/media/serve/` に対して実効させるようコードを変更する
  - `terraform/cloudflare_media_cache.tf` の `cloudflare_ruleset.directus_assets_cache` を対象に、`/api/media/serve/` への 302 が `Cache-Control` や `Set-Cookie` の有無によらず確実にキャッシュされるよう `action_parameters` を調整する (`origin_cache_control` の明示、ルール一致順の見直し等)
  - `/api/media/file/*` (実ファイル本体) の既存のキャッシュ挙動を変更しない
  - 完了状態: 変更がコミットされ、対象を限定した plan で該当ルールの差分のみが示されること
  - _Requirements: 9.1, 9.2, 9.3_

- [x] 0.2 適用しキャッシュが有効であることを検証する
  - 対象を限定して apply する
  - `/api/media/serve/{id}/{size}` への 2 回目以降のリクエストで `cf-cache-status: HIT` を確認する
  - キャッシュされた 302 をブラウザで開き、画像が正常に表示されることを確認する
  - 構内マップで同一区画を複数回タップし、CMS 側のリクエスト数が画像枚数に比例して増えないことを確認する
  - `Location` が署名付き URL でないことを踏まえた TTL であることを記録する。将来署名付き URL に変わった場合は TTL をその有効期限未満に短縮する
  - Cloudflare のキャッシュパージによる無効化手段を確認し記録する
  - 完了状態: HIT・画像の正常表示・リクエスト増幅の抑制の 3 点が確認され記録されていること
  - _Requirements: 9.4, 9.5, 9.6, 9.7, 9.8_
  - _Depends: 0.1_

- [x] 1. ベースライン測定の基盤整備と実測

- [x] 1.1 ブレークポイント探索用の負荷シナリオを用意する
  - CMS の API を対象とし、段階的にレートを上げ続ける構成とする。plateau と ramp-down を設けない
  - 応答が遅延してもレートが落ちない executor を用いる
  - エラー率の閾値超過で自動停止する設定を入れる。本番へ印加するため、壊れた後も負荷を掛け続けない
  - 対象ベース URL を切り替えられるようにし、Cloudflare を経由する経路と経由しない経路の双方で同一シナリオを使えるようにする
  - 完了状態: シナリオを短時間・低レートで試走させ、リクエストが送信されメトリクスが出力されること
  - _Requirements: 1.1, 1.6, 1.7_

- [x] 1.2 オリジン直経路でブレークポイントを実測する
  - Cloudflare を経由しない経路から負荷を印加する
  - HTTP 5xx またはタイムアウトが発生し始めたレートを記録する
  - 実行中のノードのメモリ使用量・CPU 使用率・Pod の OOMKilled 発生有無・CMS と cms-db のレスポンス劣化を記録する
  - 実行前に CNPG バックアップの正常性を確認し、利用の少ない時間帯に実施する
  - 測定値が実行元の回線帯域に律速していないことを確認する
  - 完了状態: ブレークポイントに到達したレートと、その時点のエラー種別・リソース使用状況が記録されていること
  - _Requirements: 1.2, 1.3, 1.4, 1.6_

- [x] 1.3 Cloudflare 経由の経路を測定しエッジキャッシュの効果を確認する
  - 短時間かつ小規模に留める。レート制限や WAF の判定に触れることを避ける
  - オリジン直の結果と区別して記録する
  - 完了状態: 両経路の結果が別々に記録され、エッジキャッシュがオリジン負荷をどの程度吸収しているかを説明できること
  - _Requirements: 1.2_

- [x] 1.4 合格ラインを算出しステートレス分散の要否を判定する
  - 公開サイトを 1 ページ閲覧した際に CMS API へ発生するリクエスト数を実測する。Workers のキャッシュ設定に依存して大きく変動するため推定しない
  - 来場者数と 1 人あたり平均ページビュー数を実績値から取得する
  - 設計が定義する算出式と係数により合格ラインを求める
  - ブレークポイントが合格ラインを上回る場合はステートレス分散を見送る判断を記録する
  - この判定がデータ層の冗長化には影響しないことを記録に明記する
  - 算出に用いた実績値を公開リポジトリ配下の文書へ記載しない
  - 完了状態: 合格ラインの数値と判定結果が算出過程とともに記録され、タスク 5.8 の実施可否が確定していること
  - _Requirements: 1.5, 1.8, 1.9_

  - 既存ノードには現行値を明示し、実体との差分を生じさせない
  - 追加ノード 2 台のエントリを定義する。プライベート IP は既存サブネットの未使用アドレスから割り当てる
  - 完了状態: 対象を限定した plan で追加ノード 2 台のみが新規作成として示され、既存ノードに差分が出ないこと
  - _Requirements: 2.1, 2.3, 2.4, 2.7_

- [x] 2.2 spread 型の placement group を定義し全ノードの所属先とする
  - spread 型の placement group リソースを新規に定義する
  - 全ノードがこれに所属するようノード定義から参照する
  - 既存ノードの所属変更が再作成ではなく in-place の更新として示されることを plan で確認する
  - 完了状態: plan において既存ノードの差分が所属先の変更のみであり、再作成が示されないこと
  - _Requirements: 2.2, 2.3, 2.4_
  - _Depends: 2.1_

- [x] 2.3 (P) 追加ノードを server グループとして登録する
  - 追加ノードを既存 playbook の該当グループとして inventory に定義する
  - 既存ノードが属するグループの内容を変更しない。join 先の解決がこのグループの先頭要素に依存するため
  - 対象を限定した check 実行により、既存ノードに変更が生じないことを確認する
  - 完了状態: check 実行が追加ノードのみを対象とし、既存ノードに対して変更なしと報告すること
  - 実機のない間は inventory から外しておく (`k3s_server_worker` は空)。未作成のホストが残ると `any_errors_fatal` の Play が unreachable で全台分中断し、k3s-bootstrap と k3s-upgrade が `prod-node-1` を含めて実行できない。タスク 5.3 で実機を作成した後、タスク 5.4 の前に追加ノードを inventory へ戻す
  - _Requirements: 2.5, 2.6, 2.7_
  - _Boundary: inventory 定義_

- [x] 2.4 (P) API 証明書の代替名を全 server ノードへ適用する
  - 代替名の設定をクラスタ初期化の分岐外へ移し、ノード種別によらず適用されるようにする
  - 設定値は各ノード自身の接続名とプライベート IP とし、他ノードの値を含めない
  - 完了状態: テンプレートの描画結果において、初期化ノードと追加ノードの双方に代替名が含まれること
  - _Requirements: 2.7, 3.5_
  - _Boundary: tls-san 適用_

- [x] 2.5 (P) 3 ノード構成中に自動復旧が起動しないことを確認する
  - `dr-trigger.yml` は通知 (Discord と `dr-incident` Issue) のみで復旧を起動しない。復旧は人が `dr-recovery.yml` を起動し、Environment `dr-recovery` の reviewer が承認した場合だけ動く
  - `dr-recovery.yml` の生存確認ゲートは、残存ノードがある複数ノード構成では停止する。ゲートの上書き (`force`) は既定で無効
  - 追加の無効化フラグは設けない。現行の仕組みが要件 6 を満たすことをコードの読解で確認し、`docs/node-scaling-runbook.md` A-2 に反映する
  - 完了状態: 自動復旧の起動経路が存在しないことと、3 ノード構成での復旧が手動手順になることが手順書に記載されていること
  - _Requirements: 6.1, 6.2, 6.5_
  - _Boundary: DR 制御_

- [x] 2.6 対象を限定した差分確認の手順を確定する
